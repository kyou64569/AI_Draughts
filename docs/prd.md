# 产品需求文档（PRD · 简单版）

**项目**：AI 中国跳棋（AI Chinese Checkers）Web 应用
**作者**：许清楚（产品经理）
**技术栈**：后端 Node/Express（API Key 留服务端）；前端 Vite + React + MUI + Tailwind CSS
**决策依据**：前置调研结论——GitHub 无现成核心架构，确定从零搭建；棋盘几何参考 zym9863/chinese-checkers 的立方坐标(q,r,s)方案（仅算法参考，自研 TS 实现），LLM 调用/解析参考 pps-apps/checkers-chat。

---

## 1. 产品目标

**一句话定位**：一款支持多 AI 模型配置与自定义 AI 玩家、可人机对战与自动观战的 Web 版中国跳棋应用，AI 决策由 LLM 提示词驱动并附带可解释的决策理由。

**成功标准**：
1. 用户可完成**模型配置 CRUD + 连通性测试**，且 **API Key 永不出现在前端**。
2. 用户可创建多个 **AI 玩家**并绑定模型配置、自定义名称。
3. 可创建房间、指派 AI、**满员开赛**；规则引擎（单步/连跳/回合/胜负/积分）**100% 正确**。
4. AI 决策由 LLM 返回，经**合法性校验 + 兜底走法**，对局可完整跑通不卡死。
5. 桌面与移动端**响应式**可用，决策理由日志可查看。

---

## 2. 用户故事

**角色**：平台管理员（管理模型配置、AI 玩家）、建房者=普通用户（创建房间、指派 AI、亲自走子）、观战者（观看 AI 自动对战）。

1. **[管理员]** 作为平台管理员，我希望能新增/编辑/删除大模型配置（名称、Base URL、API Key），并能拉取可用模型列表与测试连通性，以便为 AI 玩家提供可用的模型后端。
2. **[管理员]** 作为平台管理员，我希望能创建多个 AI 玩家、绑定某一模型配置与具体模型并自定义名称，以便在对局中调用不同风格/能力的 AI。
3. **[建房者]** 作为建房者，我希望能选择对局模式（人机 1 人 + 2 AI / 观战 3 AI）并创建房间，以便发起一局跳棋。
4. **[建房者]** 作为建房者，我希望能为房间座位指派已创建的 AI 玩家，满员后开始对局，以便按预期阵容开赛。
5. **[玩家]** 作为建房者/玩家，我希望在牌桌上看到三方棋子、自己可选择单步或连跳走子，系统正确流转回合、判定胜负并结算积分，以便获得合规对局体验。
6. **[观战者]** 作为观战者，我希望进入观战模式后看到 3 个 AI 自动对战、实时棋子移动与每手决策理由日志，以便理解 AI 博弈过程。
7. **[所有用户]** 作为任何用户，我希望在桌面和移动端都能正常使用（响应式），以便随时访问。
8. **[建房者]** 作为建房者，我希望当某 AI 决策超时或返回非法走法时系统有兜底走法保证对局不中断，以便对局流畅完成。

## 3. 需求池（P0 / P1 / P2）

> P0 = Must have（核心不可妥协）；P1 = Should have；P2 = Nice to have。每条含**编号、标题、描述、验收标准**。

### P0（Must have）

**P0-1 模型配置管理 CRUD**
- 描述：提供模型配置的增删改查。字段含：配置名称、Base URL、API Key、默认模型。支持调用模型提供方接口**拉取可用模型列表**供下拉选择；提供**连通性测试**按钮（后端代理请求，返回成功/失败与延迟）。
- 验收：(1) 可新增/编辑/删除/列表查看配置；(2) 点"拉取模型"返回该 Base URL 下的可用模型列表供选择；(3) 点"测试连通性"返回状态（成功/失败 + 耗时）；(4) 列表/表单**不展示 API Key 明文以外的敏感泄露**，编辑时可覆盖。

**P0-2 AI 玩家管理 CRUD**
- 描述：创建多个 AI 玩家，每个绑定一个**模型配置**并选择具体**模型**，自定义玩家名称。支持列表增删改查。
- 验收：(1) 新建 AI 玩家时可从已有模型配置中选择其一，并选择其下具体模型；(2) 列表显示名称、绑定配置、绑定模型；(3) 可编辑（改名/换绑）与删除；(4) 删除被房间占用的 AI 玩家需有保护/提示。

**P0-3 规则引擎正确性**
- 描述：实现完整中国跳棋规则——单步移动（邻位空格）、连跳（沿直线反复跳跃，必须跳到无子可跳为止，不可中途停留）、回合流转、胜负判定（己方棋子全部到达对面营地/满营）、积分结算。棋盘采用立方坐标(q,r,s)几何，三方各占一个角。
- 验收：(1) 单元测试覆盖规则边界：单步仅限相邻空位；连跳不可中途停；无合法走法判该方无法行动（按规则处理）；满营判胜；(2) 同一时刻仅当前方走子；(3) 连跳序列校验为一条合法链。

**P0-4 LLM 决策合法性校验 + 兜底**
- 描述：AI 决策通过提示词传入**棋盘全部棋子状态 + 上一手落子 + 规则约束**，解析模型返回并做**合法性校验**；若返回非法、超时或解析失败，采用**兜底走法**（如规则引擎优选走法：最大前进距离 / 最多连跳吃子）。
- 验收：(1) Prompt 含完整棋盘状态与上一手；(2) 构造非法返回时系统自动采用兜底，对局不中断；(3) 兜底日志被记录并可区分"AI 决策"与"兜底"。

**P0-5 API Key 不泄露前端**
- 描述：所有 LLM 调用、模型列表拉取、连通性测试**一律走后端代理**；API Key 仅存服务端（配置文件/环境变量），前端不可见、不可通过网络请求外泄。
- 验收：(1) 浏览器 Network 中任何请求均不含第三方 API Key，只发往自身后端；(2) 前端源码与打包产物无可检索的 Key；(3) 后端日志/报错不向客户端回传 Key。

**P0-6 房间与游戏流程（满员开赛 + 完整规则落地）**
- 描述：仅用户可创建房间并为座位指派 AI；满员开始。集成规则引擎与 AI 决策，实现完整对局闭环。人机模式：1 人类座位 + 2 AI；观战模式：3 AI 自动对战。
- 验收：(1) 建房者可创建房间并看到座位面板；(2) 指派 AI 到座位，满员后方可"开始"；(3) 开赛后按规则引擎流转，AI 座位由 LLM 决策驱动（人类座位由建房者手动走子）；(4) 对局结束触发胜负判定与积分结算。

### P1（Should have）

**P1-1 人机模式（1 人 + 2 AI）**
- 描述：建房者作为人类玩家，2 个 AI 座位自动决策；人类可点击选择合法单步或连跳。
- 验收：(1) 人类仅能在其回合走合法步；(2) 两 AI 座位按 LLM 决策自动行动；(3) 混合回合流转正确。

**P1-2 观战模式（3 AI 自动对战）**
- 描述：无人类玩家，3 个 AI 座位自动对战，进入即满员开赛。
- 验收：(1) 创建观战房间即满员（3 AI）；(2) 全程自动推进无需人工；(3) 观战者可实时观看。

**P1-3 牌桌可视化与决策日志**
- 描述：六角星棋盘 + 三方棋子可视化牌桌；展示 AI 思考过程与**决策理由日志**（每手：思考摘要 + 选择走法 + 理由）。
- 验收：(1) 棋盘清晰区分三方棋子颜色与座位；(2) 每手 AI 落子同步展示思考/理由；(3) 日志可滚动、按时间顺序查看。

**P1-4 AI 决策提示词规范**
- 描述：定义统一的 Prompt 结构：棋盘状态编码（q,r,s + 占位）、上一手落子、规则约束说明、输出格式（结构化 JSON：from/to/reason）。
- 验收：(1) 文档定义输入/输出 schema；(2) 解析器严格按 schema 工作并做校验；(3) 不同模型配置复用同一规范。

### P2（Nice to have）

**P2-1 移动端体验优化**：触控热区放大、抽屉式日志、布局自适应。
- 验收：移动端可完成创建房间、指派 AI、走子全流程。

**P2-2 历史对局与积分排行**：保存对局结果与积分，展示名次。
- 验收：可查看历史对局列表与累计积分/排名。

**P2-3 配置导入导出**：模型配置 / AI 玩家导出 JSON 并可导入备份。
- 验收：导出文件可被重新导入还原。

**P2-4 决策日志导出/复盘**：单局日志导出为文件供复盘。
- 验收：可下载某局完整决策日志。

## 4. UI 设计要点

**关键页面**
1. **模型配置页**：配置列表（名称/Base URL/模型数/操作）+ 新增/编辑表单（名称、Base URL、API Key、模型下拉、连通性测试按钮）。
2. **AI 玩家页**：玩家列表（名称、绑定配置、绑定模型、操作）+ 新增表单（名称、选择模型配置、选择模型）。
3. **房间页**：模式切换（人机 / 观战）、房间列表、创建房间、座位指派面板（拖拽/下拉绑定 AI 玩家）、开始按钮（满员可用）。
4. **对局牌桌页**：六角星棋盘（三方用色区分）、座位/玩家信息卡（名称、积分、状态）、当前回合指示、AI 思考中状态、决策理由日志侧栏（可滚动）、积分榜。

**信息架构**
- 顶部导航：模型配置 / AI 玩家 / 房间 / 对局（牌桌）。
- 流程：管理后台（模型配置 → AI 玩家）→ 房间（模式/创建/指派）→ 对局（牌桌 + 决策日志）。

**响应式要点**
- 桌面：三栏布局——棋盘居中，左侧座位/玩家信息，右侧决策日志。
- 移动端：棋盘置顶、玩家信息卡在棋盘上方；决策日志改为可折叠底部抽屉；走子点击热区放大，避免误触。
- 断点：以 Tailwind 默认断点为主，关键交互在 ≤768px 单独适配。

## 5. 已确认决策（主理人拍板）

> 原"待确认问题"5 项已由主理人拍板，以下为最终决策，作为后续设计与实现的硬约束。

**决策 1 · 积分结算公式**（三人局，每座位=一个玩家）
- 基础分 `base = 到达目标营地棋子数 × 100`（10 子全到 = 1000）。
- 名次加成 `rank`：第 1 名 +300，第 2 名 +150，第 3 名 +50。
- 用时惩罚 `timePenalty = ⌊总对局秒数 / 30⌋ × 5`（向下取整，最低 0）。
- 总分 `score = max(0, base + rank − timePenalty)`。
- 胜负：最先让全部 10 子到达对面营地的玩家为第 1 名；其余按完成先后/进度排名。
- 排名范围：人机模式 3 个座位（1 人 + 2 AI）全部计入排名；观战模式仅 3 个 AI 计入排名。

**决策 2 · 房间满员判定**
- 严格"满员开始"，**不允许房主强制开赛例外**。
- 人机模式 = 1 人类座位 + 2 AI 满员开赛；观战模式 = 3 AI 满员开赛；**未满不可开赛**（不自动补位、不让人顶替 AI）。

**决策 3 · 连跳规则**
- 与需求一致——连跳一旦开始必须跳到无子可跳为止（不可中途停留）；单步移动与连跳是两种独立走法，玩家可选择只单步。书面确认无歧义。

**决策 4 · AI 兜底策略**
- 单次 LLM 决策**超时阈值 = 30 秒**，超时即走兜底。
- 返回解析失败 / 走法非法：用更严格提示词**重试 1 次**；仍失败 → 兜底。
- 同一 AI **连续 3 次失败** → 标记"托管(auto-pilot)"，此后该座位全部走法由确定性兜底算法生成，**不再调用 LLM**（避免卡死）；UI 展示托管标记。
- 兜底走法算法（确定性）：① 优先"连跳"走法（推进距离最大、收益最高）；② 若无连跳，选使某棋子向自身目标营地"前进距离最大"的单步；③ 等价取第一个；④ 理论上单步永远存在（除非被完全围死且无空邻格，极罕见），若真无合法走法则**跳过该回合(skip turn)**。

**决策 5 · AI 决策并发**
- 3 个 AI **串行决策**（房间回合制，轮到某 AI 座位才调用其绑定模型，天然串行），无需并发队列。
- 后端对同一 `baseURL` 的调用建议加**最小间隔（≥ 800ms）**以防限流。
- LLM 请求走 **OpenAI 兼容 `/v1/chat/completions`**。
